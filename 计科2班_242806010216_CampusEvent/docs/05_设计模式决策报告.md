## 1. 设计目标

1. 报名规则可替换，不在服务层堆积 `if 活动类型` 分支；
2. 报名业务与通知渠道解耦，通知故障不影响报名数据；
3. 职责边界清晰，便于测试与后续需求变更；
4. 在满足需求的前提下控制复杂度，不引入消息队列、微服务等额外设施。

## 2. 决策一：策略模式表达报名规则

### 2.1 结构

- 抽象：`RegistrationPolicy.decide(RegistrationContext) -> PolicyDecision`
- 实现：`DirectRegistrationPolicy`、`ApprovalRegistrationPolicy`
- 上下文：`RegistrationContext`（活动、学生、已通过人数、剩余名额）
- 工厂：`RegistrationPolicyFactory` 按 `Activity.policy_type` 返回策略

### 2.2 为什么把名额检查放在策略中

初始需求中两类规则对名额的处理不同：

- 直接报名：名额不足时立即失败；
- 审核报名：提交阶段允许进入待审核，待审核不占名额；批准时才检查名额。

如果把名额检查放在 `RegistrationService` 的公共前置校验中，审核型报名会在满员时被错误拒绝；如果放在服务层再用类型分支区分，则新增规则时必须修改服务，违背开闭原则。因此：

- **与策略无关的公共规则**（活动存在、未开始、重复报名）留在服务层；
- **与报名结果强相关的名额判断**由策略负责，并通过 `RegistrationContext.remaining` 复用统一计算。

### 2.3 备选方案比较

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 服务层 `if/elif` 判断活动类型 | 类少、实现直接 | 新增规则必须改服务；测试分支多；易漏改 | 否决 |
| 策略模式 + 工厂 | 新增规则只加类并注册；服务依赖抽象；可单测 | 类数量增加，调用链略长 | 采用 |
| 规则引擎/配置化 DSL | 规则可热配置 | 对本课程规模明显过度设计 | 否决 |

### 2.4 成本与扩展

- **成本**：多出接口、上下文、决策对象和工厂，约 4 个类；阅读者需要理解依赖倒置。
- **收益**：新增一种报名规则时，预期只需新增策略类 + 注册 + 页面选项，服务主流程无需修改。
- **可测性**：策略可脱离数据库单独测试；服务层测试可注入假策略。

## 3. 决策二：观察者/事件总线解耦通知

### 3.1 结构

- `RegistrationEvent`：事件 ID、类型、学生、活动、消息文本、时间；
- `EventBus.publish`：幂等检查 → 逐个调用 `EventHandler`；
- `SiteMessageHandler`：订阅者，写入 `messages` 表；
- `EventLogRepository`：`dispatched_events` 表以 eventId 主键去重；
- `NotificationFailureRepository`：记录处理器异常。

### 3.2 事务边界

```
with conn:                      # 报名状态提交
    registration = repo.create(...)
event_bus.publish(event)        # 提交后再通知
```

- 若通知失败，报名已提交，不会出现“消息有了但报名没有”或“报名回滚导致消息孤儿”；
- 失败只留痕，用户报名仍然有效；
- 反过来，如果业务要求“通知成功才算报名成功”，应把通知纳入事务或使用本地消息表 + 重试；本项目按指导书要求选择“通知失败留痕、不影响报名”。

### 3.3 避免重复通知

1. 每个状态变更只创建一个事件，事件在服务成功提交后发布；
2. `dispatched_events(event_id PRIMARY KEY)` 做持久化幂等，重复发布直接跳过；
3. 状态机限制重复审批/重复取消，避免产生重复业务事件；
4. 页面使用 POST-Redirect-GET，降低用户刷新造成的重复提交。

### 3.4 备选方案比较

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 服务内直接写消息表 | 简单 | 业务与通知耦合，新增渠道要改服务 | 否决 |
| 观察者/事件总线（进程内） | 解耦、易扩展、无需中间件 | 无跨进程可靠性，需要自己做幂等/失败留痕 | 采用 |
| 消息队列 | 可靠、可削峰 | 课程环境过重，运维成本高 | 否决 |

## 4. 决策三：工厂与仓储

- **工厂**：把“字符串 → 策略实例”的映射集中管理，路由/模板只依赖选项列表；非法类型在创建活动时即被拒绝。
- **仓储**：所有 SQL 集中在 `repositories.py`，服务层只表达业务规则；测试可用临时 SQLite 文件复现。
- **服务层**：控制事务、权限外的业务校验、事件发布顺序，避免路由层承担业务逻辑。

## 5. SOLID 对照

| 原则 | 体现 |
| --- | --- |
| SRP 单一职责 | 策略只决定报名结果；服务编排流程；仓储只做持久化；处理器只写通知 |
| OCP 开闭原则 | 新增报名规则/通知渠道以新增类为主，尽量不改服务主流程 |
| LSP 里氏替换 | 两种策略都遵守 `RegistrationPolicy` 契约，可在服务中互换 |
| ISP 接口隔离 | `RegistrationPolicy`、`EventHandler` 都是窄接口 |
| DIP 依赖倒置 | 服务依赖策略抽象；事件总线依赖处理器抽象；仓储隔离数据库 |

## 6. 状态与边界决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 待审核是否占名额 | 不占 | 指导书 B.2 明确；批准时再检查 |
| 取消已通过报名 | 允许（含活动开始后） | 指导书只禁止开始后新增报名；历史保留，可重新申请 |
| 删除有报名的活动 | 软删除 | 保留历史报名/通知，避免外键与审计丢失 |
| 通知失败 | 留痕、不回滚报名 | 指导书 B.2 第 6 条；保证合法报名不消失 |
| 重复有效报名 | 服务校验 + 部分唯一索引 | 应用层提示友好，数据库层兜底并发 |
| 时区 | 服务器本地时间 | 课程演示简化；部署文档要求设置 `Asia/Shanghai` |

## 7. 已知代价与后续观察点

1. 事件总线是进程内的，进程崩溃时“报名已提交、通知未写入”只能靠失败日志发现，没有自动重试；
2. 策略上下文目前只包含活动与人数，若未来规则依赖学生画像/信用分，需要扩展上下文对象；
3. 软删除使查询必须带 `is_deleted = 0` 条件，仓储已统一封装；
4. 报名列表存在 N+1 统计查询，演示规模可接受；数据量增大后可改为聚合查询；
5. 这些代价将在需求变更后通过“新增类数、修改核心类数、回归失败数”等指标继续评估。
