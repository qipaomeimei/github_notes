## 3. 用例详情

### UC-01 创建活动

- **参与者**：管理员
- **前置条件**：管理员已登录。
- **触发**：在“活动管理”点击“新建活动”并提交表单。
- **主流程**：
  1. 系统展示活动表单；
  2. 管理员填写名称、类型、时间、地点、人数上限、报名方式、介绍；
  3. 系统校验必填项、长度、名额为正整数、时间晚于当前时间、报名方式合法；
  4. 系统保存活动并跳转到活动详情。
- **异常流程**：
  - 任一字段非法：不写库，页面保留输入并显示中文错误；
  - 报名方式不在策略注册表中：拒绝保存。
- **后置条件**：活动状态为“报名中”，学生端可见。
- **关联规则**：BR-01、BR-02。

### UC-02 编辑活动

- **参与者**：管理员
- **前置条件**：活动存在且未下架。
- **主流程**：打开编辑页 → 修改字段 → 系统执行与创建相同的校验 → 更新成功。
- **异常流程**：活动已下架或不存在时返回 404；非法输入时保留表单并提示。
- **后置条件**：活动信息更新，已有报名记录不受影响。

### UC-03 下架活动

- **参与者**：管理员
- **前置条件**：活动存在。
- **主流程**：点击“下架”并二次确认 → 系统将 `is_deleted` 置 1。
- **后置条件**：
  - 学生端列表与详情不再展示；
  - 历史报名、消息、统计仍保留；
  - 管理员详情显示“已下架”，不能继续审批。
- **设计说明**：采用软删除而非物理删除，避免历史数据丢失。

### UC-04 浏览与搜索活动

- **参与者**：学生
- **前置条件**：学生已登录。
- **主流程**：
  1. 系统按活动时间升序展示活动卡片；
  2. 学生输入名称关键字搜索；
  3. 系统返回名称包含关键字的未下架活动；
  4. 学生点击进入详情，查看介绍、名额、报名方式与自己的报名状态。
- **异常流程**：无匹配结果时显示空状态提示。

### UC-05 直接报名

- **参与者**：学生
- **前置条件**：已登录；活动未下架、未开始；本人无有效报名。
- **主流程**：
  1. 学生在详情页点击“立即报名”；
  2. 系统校验活动状态与重复报名；
  3. 系统统计已通过人数；
  4. `DirectRegistrationPolicy` 判断名额，充足则返回“已通过”；
  5. 系统保存报名并提交事务；
  6. 系统发布 `RegistrationApproved` 事件，站内消息处理器写入消息。
- **异常流程**：
  - 名额已满：返回“名额已满，无法报名”；
  - 已有待审核/已通过报名：返回“请勿重复提交”；
  - 活动已开始：返回“活动已开始，不能报名”。
- **后置条件**：报名状态“已通过”，名额统计 +1，学生收到站内消息。

### UC-06 提交审核型报名

- **参与者**：学生
- **前置条件**：同 UC-05。
- **主流程**：
  1. 学生点击“提交报名申请”；
  2. 系统执行公共校验；
  3. `ApprovalRegistrationPolicy` 返回“待审核”；
  4. 系统保存报名并发布 `RegistrationPending` 事件；
  5. 学生收到“待审核”站内消息。
- **异常流程**：与 UC-05 相同；待审核阶段不因名额满而拒绝。
- **后置条件**：报名状态“待审核”，不占用名额。

### UC-07 审批报名

- **参与者**：管理员
- **前置条件**：管理员已登录；报名状态为“待审核”；活动未下架。
- **主流程（批准）**：
  1. 管理员在活动详情筛选待审核记录；
  2. 点击“批准”；
  3. 系统校验报名状态、活动状态，再次统计已通过人数；
  4. 名额未满则将状态更新为“已通过”；
  5. 发布 `RegistrationApproved` 事件并写入站内消息。
- **主流程（拒绝）**：
  1. 管理员点击“拒绝”并确认；
  2. 状态更新为“已拒绝”；
  3. 发布 `RegistrationRejected` 事件并写入站内消息。
- **异常流程**：
  - 名额已满：批准失败，状态保持“待审核”，提示管理员；
  - 活动已下架：拒绝审批；
  - 状态不是待审核：拒绝操作（防止重复审批）。
- **后置条件**：状态与统计同步变化。

### UC-08 取消报名

- **参与者**：学生
- **前置条件**：报名属于本人，状态为“待审核”或“已通过”。
- **主流程**：在“我的报名”或活动详情点击取消并确认 → 状态更新为“已取消” → 生成取消通知 → 统计同步更新。
- **异常流程**：报名不存在/不属于本人、状态已拒绝/已取消时提示不可取消。
- **后置条件**：已取消记录保留为历史，学生可再次申请同一活动。

### UC-09 查看站内消息

- **参与者**：学生
- **主流程**：进入消息页查看报名/审核结果 → 可将单条或全部消息标为已读。
- **后置条件**：导航未读数同步减少。

### UC-10 查看报名统计

- **参与者**：管理员
- **主流程**：在活动管理列表或详情查看已通过、待审核、剩余名额。
- **计算规则**：已通过 = `status='approved'` 的数量；待审核 = `pending` 数量；剩余 = max(容量 − 已通过, 0)。

## 5. 关键边界

| 场景 | 处理方式 |
| --- | --- |
| 同一学生重复提交 | 服务校验 + 数据库部分唯一索引，双保险 |
| 多个待审核申请竞争最后名额 | 批准时重新统计已通过人数；后批准者失败 |
| 通知失败 | 报名事务已提交；失败写入 `notification_failures`，不删除报名 |
| 管理员删除有报名的活动 | 软删除，历史保留 |
| 活动已开始 | 禁止新增报名；已有记录保留 |
| 并发报名 | SQLite 写锁 + 唯一索引；捕获 `IntegrityError` 转为业务提示 |
