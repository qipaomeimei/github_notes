## 1. 变更请求

| 编号 | 变更描述 | 业务价值 |
| --- | --- | --- |
| CR-01 | 新增“候补报名”规则：活动满员后学生可加入候补队列；已通过报名被取消时，按加入顺序自动递补最早候补者并通知；活动已开始或已下架时不再递补 | 减少满员活动的名额浪费，避免管理员手工补录 |
| CR-02 | 新增邮件通知渠道：报名、审核、取消、候补、递补事件同时写入模拟邮件发件箱 `email_outbox`；学生邮箱为空时跳过 | 验证观察者机制能否在不修改报名业务的前提下扩展通知渠道 |

两条变更分别针对“策略维度”和“通知维度”，正好检验 baseline-v1 的两处设计是否真正可扩展。

## 3. 设计决策

| 决策点 | 选择 | 理由 | 备选方案与否决原因 |
| --- | --- | --- | --- |
| 候补规则放在哪里 | 新增 `WaitlistRegistrationPolicy` 实现 | 与“直接/审核”同属报名结果产生规则，服务仍只依赖 `RegistrationPolicy` 抽象 | 在 `RegistrationService` 内写 `if policy_type == "waitlist"`：会破坏开闭原则，后续每加一种规则都要改核心服务 |
| 候补名额是否占容量 | 候补**不占**名额，只有 `APPROVED` 计数 | 与 B.2“名额按已通过计算”一致 | 候补占名额会导致实际可选人数变少，语义错误 |
| 递补何时发生 | 已通过报名取消时，在同一数据库事务内递补 | 避免“名额已空但队列未动”的中间态 | 定时任务扫描：课程项目引入调度器，复杂且演示环境无必要 |
| 递补顺序 | `created_at ASC, registration_id ASC` | 同一秒内提交时用自增 ID 保证稳定顺序 | 仅按 `created_at`：秒级时间戳可能相同，顺序不确定 |
| 活动开始/下架后是否递补 | 不递补 | 活动已开始递补无意义；下架活动不应再产生新有效名额 | 仍递补：会造成已下架活动出现新“已通过”记录 |
| 邮件如何发送 | 写入 `email_outbox` 模拟排队 | 课程环境无 SMTP，且可被自动化测试精确断言 | 直接调用 SMTP：测试不可复现，可能泄露凭据 |
| 邮件渠道如何接入 | 新增一个 `EventHandler` 实现 | 观察者机制的直接收益：报名服务不需要知道邮件存在 | 在 `RegistrationService` 中直接发邮件：通知与业务再次耦合 |
| 老数据库怎么办 | `_apply_migrations` 幂等升级 | 云服务器可能已有 baseline-v1 数据，不能要求清库 | 直接删库重建：会丢失历史报名，不符合持久化要求 |

### 3.1 关键事务边界

```
BEGIN
  UPDATE registrations SET status='cancelled' WHERE ...
  SELECT 最早 waitlisted 记录
  UPDATE registrations SET status='approved' WHERE ...
COMMIT
  → 发布 registration.cancelled 事件
  → 发布 registration.promoted 事件
```

- 取消与递补必须同事务：否则可能出现“取消已提交、递补失败”，名额空置；
- 事件在事务提交后发布：通知失败不会回滚报名或递补；
- `EventBus` 仍按 `event_id` 幂等，取消与递补是两个不同事件，各自只通知一次。

## 6. 风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 递补导致超员 | 候补转已通过后超过容量 | 递补前重新统计 `approved`；仅 `approved < capacity` 才递补 |
| 唯一索引与候补冲突 | 同一学生同时存在候补与其他有效报名 | 迁移索引把 `waitlisted` 纳入有效状态；重复报名由服务层和索引双重拦截 |
| 迁移失败或重复执行 | 云服务器启动失败 | `_apply_migrations` 先检测列/索引是否存在，幂等执行；新库由 `schema.sql` 直接创建 |
| 邮件渠道异常影响报名 | 报名丢失 | 沿用“先提交、后发布”；`EventBus` 捕获异常写 `notification_failures`，不回滚 |
| 递补后通知失败 | 学生不知道自己已递补 | 报名状态已提交，学生可在“我的报名”看到“已通过”；失败记录可追踪 |
| 老数据没有邮箱 | 邮件渠道静默跳过 | 迁移为演示学生补默认邮箱；真实学生为空时跳过，不影响站内消息 |

## 8. 反思结论

1. **修改范围合理**：CR-01 需要改变“报名结果如何产生”，因此新增策略实现；CR-02 需要增加“通知渠道”，因此新增订阅者。二者都落在既有扩展点内，没有推倒重来。
2. **模式收益**：报名服务不需要知道候补和邮件的存在，新增规则/渠道以“加类 + 注册”为主；`baseline-v1` 的抽象在变更中被真实使用，而不是装饰。
3. **模式成本**：类与文件数量增加，阅读链路变长（页面 → 服务 → 策略/事件 → 处理器 → 仓储）；候补递补涉及事务和事件两类一致性，必须靠测试锁定。
4. **仍需人工判断**：候补不占名额、开始后不递补、取消与递补同事务等规则，无法由 AI 自动推导，必须由设计者依据业务语义决定。
