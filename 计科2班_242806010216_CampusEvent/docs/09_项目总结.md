## 1. 实验目标与需求范围

### 1.1 实验目标

本项目以 CampusEvent 为载体，完成“设计先行、AI 辅助实现、需求变更、回归测试”的完整闭环，重点验证：

1. 能否从需求中识别领域对象、服务与职责边界，并画出可读的 UML 类图；
2. 能否用策略模式隔离变化的报名规则，用观察者/事件机制解耦通知；
3. 能否在需求变更时控制修改范围，并用客观指标说明设计收益与成本；
4. 能否用自动化测试保证初始功能与变更后功能同时正确。

### 1.2 初始需求范围（P2-F01 ～ P2-F08）

| 编号 | 功能 | 实现要点 |
| --- | --- | --- |
| P2-F01 | 活动管理 | 管理员创建、编辑、软删除；校验名称、类型、时间、地点、容量、报名方式 |
| P2-F02 | 活动查看 | 学生浏览列表与详情，按名称搜索 |
| P2-F03 | 报名/取消 | 报名、取消；同一活动禁止重复有效报名 |
| P2-F04 | 报名策略 | 直接报名自动通过；审核型进入待审核 |
| P2-F05 | 审批 | 管理员批准/拒绝；批准时复查名额 |
| P2-F06 | 状态管理 | 待审核/已通过/已拒绝/已取消，转换受服务层约束 |
| P2-F07 | 站内通知 | 报名与审核结果写入站内消息 |
| P2-F08 | 统计 | 已通过、待审核、剩余名额 |

### 1.3 明确不做（范围外）

- 不做用户注册、找回密码、复杂 RBAC；
- 不做真实邮件/短信网关、消息队列、分布式事务；
- 不做移动 App、第三方日历同步；
- 不实现教师端以外的多租户与组织架构。

范围外功能即使 AI 建议也不纳入，避免项目膨胀。

## 2. 实现方案

### 2.1 运行环境与技术栈

| 项目 | 选择 |
| --- | --- |
| 语言 | Python 3.11+（开发与测试使用 3.14） |
| Web 框架 | Flask 3.x（应用工厂 + Blueprint） |
| 数据库 | SQLite（标准库 `sqlite3`，无 ORM） |
| 模板与样式 | Jinja2 + 原生 CSS |
| 测试 | pytest |
| 生产部署 | gunicorn（1 worker + 4 threads）+ Nginx + systemd；Windows 可用 waitress |
| 版本管理 | Git，标签 `baseline-v1`、`change-v2` |

### 2.2 系统结构

```
浏览器
  │  HTTP
  ▼
Flask 路由（auth / student / admin）── CSRF、登录与角色校验
  │
  ▼
应用服务层（ActivityService / RegistrationService）
  │             │
  │             ├── 策略抽象 RegistrationPolicy
  │             │     ├── DirectRegistrationPolicy
  │             │     ├── ApprovalRegistrationPolicy
  │             │     └── WaitlistRegistrationPolicy（v2）
  │             └── 事件总线 EventBus
  │                   ├── SiteMessageHandler
  │                   └── EmailNotificationHandler（v2）
  ▼
仓储层（Activity / Registration / Message / EmailOutbox / EventLog / Failure）
  │
  ▼
SQLite（activities、registrations、messages、email_outbox、dispatched_events…）
```

### 2.3 主要模块

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 应用工厂 | `app/__init__.py` | 配置、数据库生命周期、CSRF、错误页、`/healthz` |
| 领域模型 | `app/domain/models.py` | 活动、报名、状态、统计 |
| 策略 | `app/domain/policies.py` | 报名规则抽象、实现、工厂 |
| 事件 | `app/domain/events.py` | 领域事件、事件总线、幂等与失败留痕 |
| 服务 | `app/services.py` | 校验公共规则、事务边界、发布事件 |
| 仓储 | `app/repositories.py` | 全部 SQL，隔离 SQLite |
| 通知 | `app/handlers.py`、`app/notifications.py` | 站内消息、模拟邮件、装配 |
| 路由 | `app/routes/` | 登录、学生端、管理员端 |
| 页面 | `app/templates/` | 活动、报名、审批、消息 |
| 测试 | `tests/` | C1—C19、HTTP、权限、CSRF |

### 2.4 设计模式应用

**策略模式**：`RegistrationService` 只依赖 `RegistrationPolicy.decide(context)`，具体规则由活动配置的 `policy_type` 经工厂获得。公共规则（活动存在、未开始、重复报名）留在服务层；与报名方式强相关的名额判断放入策略，因为“待审核是否占名额”“满员是拒绝还是候补”在不同策略下语义不同。

**观察者/事件总线**：报名状态提交后发布 `RegistrationEvent`，`EventBus` 分发给所有 `EventHandler`。站内消息与邮件互不依赖；通知失败写 `notification_failures`，不回滚已提交报名；`dispatched_events` 以 `event_id` 为主键保证幂等。

UML 类图与时序图见 [03_UML类图_v1.md](03_UML类图_v1.md)、[04_时序图_v1.md](04_时序图_v1.md)、[10_变更版UML类图_v2.md](10_变更版UML类图_v2.md)。

### 3.2 AI 如何参与

AI 主要承担：按已确认的接口生成代码骨架、补齐模板与校验、生成测试初稿、整理文档、排查错误。所有关键设计决策由本人确认，AI 产出必须通过测试或人工检查后才保留。代表性协作事件记录在 `AI_DEV_LOG.md`。

### 3.3 人工决策摘要

1. 拒绝把报名规则写成服务层 `if policy_type` 分支，坚持策略接口；
2. 拒绝把通知写入与报名放在同一事务，改为“先提交、后发布、失败留痕”；
3. 待审核不占名额，审批时复查容量；
4. 活动删除采用软删除，保留历史报名与通知；
5. 取消已通过报名与候补递补放在同一事务；
6. SQLite 生产部署使用单 worker 多线程，避免写锁冲突；
7. 公网只暴露 80/443，应用端口仅绑定回环地址。

| 初始质量用例 | 13 | 软删除、通知失败隔离、事件幂等、登录、权限、表单、CSRF 等 |
| 变更新增 C11—C19 | 9 | 候补、递补、候补取消、开始后不递补、邮件、空邮箱、故障隔离、幂等、迁移 |

### 4.3 缺陷与修复

| 问题 | 现象 | 修复 |
| --- | --- | --- |
| 通知与报名同事务 | 消息写入失败会回滚已合法提交的报名 | 报名先提交；事件发布放在提交后；异常写失败表 |
| 审批未复查名额 | 多条待审核同时批准可能超员 | 批准前重新统计 `approved`，满员拒绝 |
| 候补迁移遗漏 | 旧库唯一索引不含 `waitlisted`，写入候补报冲突 | `_apply_migrations` 检测并重建索引 |
| 递补中间态 | 初稿先提交取消、再单独递补，可能空出名额未处理 | 取消与递补合并到同一事务 |
| 多 worker 写锁 | SQLite 多进程写入出现 `database is locked` | 部署改为单 worker + 多线程 |

## 5. 结果分析

### 5.1 可维护性对照（3.7 必做指标）

| 指标 | baseline-v1 | change-v2 | 结论 |
| --- | --- | --- | --- |
| 新增类数 | — | 3 | `WaitlistRegistrationPolicy`、`EmailNotificationHandler`、`EmailOutboxRepository` |
| 修改的核心业务类数 | — | 2 | `RegistrationService`、`ActivityService` |
| 未修改的扩展点 | — | `RegistrationPolicy` 抽象、`EventHandler`、`EventBus`、`SiteMessageHandler`、全部路由 | 变更被既有扩展点吸收 |
| 数据库变更 | — | `students.email`、`email_outbox`、唯一索引调整 | 通过幂等迁移完成 |
| 新增测试 | 23 | 9 | 全部通过 |
| 回归失败数 | 0 | 0 | 32/32 通过 |
| 代表性 AI 协作轮次 | 6 | 4（累计 10） | 见 `AI_DEV_LOG.md` |
| 修改总时长（估算） | — | 约 5～6 小时 | 含分析、编码、测试、文档与图表 |

### 5.2 模式的收益

1. **新增报名规则不改主流程**：候补策略只需实现接口并注册，服务没有新增 `if 活动类型`；
2. **新增通知渠道不改业务**：邮件订阅者只需实现 `handle`，报名服务完全不知道邮件存在；
3. **故障隔离**：邮件渠道故障时，报名与站内消息仍然成功，失败可追踪；
4. **可测试性**：策略、事件、仓储都可独立测试，C1—C19 可在秒级完成。

### 5.3 模式的成本

1. 类与文件数量增加，阅读链路变长；
2. 事件机制带来“最终一致”的理解成本：报名已成功但通知可能失败；
3. 候补递补同时涉及数据库事务与事件发布，必须靠测试锁定边界；
4. 对简单项目而言，策略/观察者存在过度设计风险；本项目因明确存在两类规则与两类通知，收益大于成本。

### 5.4 与需求的对应

| 需求 / 变更 | 实现位置 | 验证 |
| --- | --- | --- |
| P2-F04 报名策略 | `domain/policies.py` | C1、C2、C4、C5 |
| P2-F05 审批 | `RegistrationService.approve/reject` | C6、C7、C8 |
| P2-F07 站内通知 | `EventBus` + `SiteMessageHandler` | C2、C6、C7、Q2、Q3 |
| CR-01 候补与递补 | `WaitlistRegistrationPolicy` + `_promote_waitlisted` | C11—C14 |

| 数据持久化/迁移 | `schema.sql` + `_apply_migrations` | C10、C19 |

## 6. 问题与反思

### 6.1 问题一：AI 首版把策略写成了服务内分支

AI 初版在 `RegistrationService.register` 中直接判断 `policy_type`，新增规则必须改核心方法。人工否决后改为 `RegistrationPolicy` 抽象 + 工厂。变更阶段新增候补策略时，服务主流程无需增加分支，证明该重构有效。

**反思**：AI 倾向“先写能跑的代码”，设计约束必须由人先给出，并在评审中固化。

### 6.2 问题二：通知失败导致报名回滚

初版把 `INSERT message` 与报名放在同一事务，消息失败会让学生“报名消失”。改为报名先提交、事件后发布，`EventBus` 捕获异常写 `notification_failures`。C17 与 Q2 验证了报名不会因通知故障丢失。

**反思**：事务边界不是代码细节，而是业务承诺；必须用测试把承诺固定下来。

### 6.3 问题三：候补递补的事务与顺序

候补需要“取消后立即补位”，若取消与递补分开提交，可能出现名额空置。最终把两者放入同一事务，并按 `created_at, registration_id` 取最早候补；活动开始或下架时不递补。C12、C14 覆盖了正常与边界。

**反思**：设计模式解决结构问题，但一致性仍要靠事务、索引和测试共同保证。

### 6.4 尚存局限

1. SQLite 适合单机演示，不支持高并发写入；
2. 通知失败只留痕，不自动重试；
3. 邮件为模拟发件箱，未接入真实 SMTP；
4. 未实现用户注册、密码找回、HTTPS 强制跳转；
5. 活动时间按服务器本地时区解释，部署时需设置 `Asia/Shanghai`。

## 7. 结论

本项目完成了实验二要求的初始版本、需求变更、回归测试与部署说明。策略模式使新增报名规则只增加类、不修改核心服务；观察者机制使新增通知渠道只增加订阅者、不修改报名业务；数据库迁移保证旧数据可平滑升级。32 个自动化测试全部通过，变更后回归失败数为 0。设计带来的类数量与理解成本是真实存在的，但在“规则会变、渠道会增”的需求下，扩展收益大于成本。
