## 2. 人工决策摘要

1. **职责边界**：公共规则（活动状态、重复报名）留在服务层；名额判断属于策略责任。
2. **事务顺序**：报名先提交，通知后发布；通知失败只留痕。
3. **数据一致性**：应用校验 + 数据库部分唯一索引双保险；审批前重新计数。
4. **删除策略**：软删除保留历史，而不是物理删除。
5. **部署边界**：SQLite 单写者，生产使用单 worker；公网只暴露 80/443。
6. **变更扩展点**：候补通过新增策略实现，邮件通过新增订阅者实现；抽象层与路由不改。
7. **候补一致性**：候补不占名额；取消与递补同事务；活动开始/下架不递补。

## 4. 未采纳的 AI 建议

| 建议 | 未采纳原因 |
| --- | --- |
| 引入 Flask-SQLAlchemy + Alembic | 课程规模小，增加依赖与迁移复杂度；直接 SQL 更利于展示事务与索引 |
| 用消息队列保证通知可靠 | 实验二明确无须消息队列，部署成本过高 |
| 把策略合并进服务类“减少类数量” | 会导致新增规则时修改核心服务，违背开闭原则，且评审已明确接口约束 |
| 使用多 worker gunicorn 提升吞吐 | SQLite 写锁会导致 `database is locked`，演示规模无必要 |
| 候补使用定时任务扫描补位 | 引入调度器与额外状态，演示环境无必要；取消时同步递补更直接 |
| 邮件直接接入真实 SMTP | 课程环境无邮件服务，测试不可复现；改为 outbox 模拟，保留替换点 |
