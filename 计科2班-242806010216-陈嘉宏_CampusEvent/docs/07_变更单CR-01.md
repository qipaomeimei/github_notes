## 1. 变更背景

初版上线后，热门活动在开放报名后很快满员，学生只能反复刷新等待他人取消，体验较差；同时活动组织方希望在站内消息之外，保留一份可查询的邮件通知记录；另外，管理员删除活动时希望保留历史报名数据以备统计。

## 2. 变更内容

### CR-01-1 候补队列（必做）

- 新增第三种报名方式：**候补报名（waitlist）**。
- 当活动名额已满时，学生可加入候补队列，系统按入队顺序分配候补位次。
- 当已通过报名被取消、名额释放时，系统**自动**将候补队列首位递补为已通过，并通知该学生。
- 候补中状态计入“有效报名”，同一学生不能重复报名同一活动。
- 报名统计需展示候补人数。

### CR-01-2 邮件通知渠道（必做）

- 在站内消息之外增加邮件通知渠道，两者同时投递。
- 通知内容需覆盖：报名提交/通过/拒绝/取消、候补入队、候补递补成功。
- 任一渠道失败不得影响报名事务；同一事件同一渠道不得重复通知。
- 管理员可查看邮件通知记录（本实验以数据库发件箱模拟邮件网关，不要求真实 SMTP）。

### CR-01-3 活动软删除（必做）

- 管理员“删除活动”改为**归档（软删除）**：活动从学生端列表与详情中隐藏，不能再报名或审批。
- 历史报名、消息、通知记录必须保留。
- 管理员可恢复已归档活动。
- 已有报名记录的活动不再因“存在报名”而被拒绝归档。

## 3. 约束与验收标准

| 编号 | 验收标准 |
| --- | --- |
| AC-1 | 活动容量为 1、候补方式：第 1 人报名 `approved`，第 2 人 `waitlisted` 且候补位次为 1 |
| AC-2 | 第 1 人取消后，第 2 人自动变为 `approved`，并收到“递补成功”通知 |
| AC-3 | 统计同时展示 approved / pending / rejected / cancelled / waitlisted / remaining |
| AC-4 | 报名成功后站内消息与邮件发件箱各有一条记录；重复事件不重复写入 |
| AC-5 | 邮件渠道异常不影响报名成功，失败在通知日志中可查 |
| AC-6 | 归档活动不出现在学生列表，学生访问详情可见“已归档”提示，报名与审批被拒绝 |
| AC-7 | 归档活动可恢复为 active，历史报名记录数量不变 |
| AC-8 | 初版 C1–C10 验收用例全部回归通过 |

## 4. 不在本次范围

- 真实 SMTP/短信网关对接；
- 候补名额过期策略、候补人数上限；
- 活动归档后的数据清理与保留期策略；
- 并发多实例部署下的分布式锁（当前为单实例 SQLite 事务）。
