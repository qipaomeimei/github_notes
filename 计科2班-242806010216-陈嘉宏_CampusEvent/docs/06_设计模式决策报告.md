## 1. 决策目标

系统存在两个明确的变化点：

1. **报名方式**（直接、审核、候补）——未来还可能增加“抽签”“邀请码”等方式；
2. **通知渠道**（站内消息、邮件，未来可能短信/微信）——渠道数量与实现会变化。

设计目标：让这两类变化以“新增代码”为主，而不是反复修改主流程；同时保证业务规则集中、可测试、可部署。以下按变化点记录候选方案比较与最终决策。

## 2. 变化点一：报名方式

### 2.1 候选方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. if/else 分支 | `register()` 内按 `policyType` 分支 | 实现最快 | 每加一种方式都要改核心方法；分支条件与名额、通知逻辑耦合；难单测 |
| B. 策略模式 | 抽象 `RegistrationPolicy.decide()`，每种方式一个类 | 符合开闭原则；策略可独立测试；主流程稳定 | 类数量增加；需要工厂/注册表选择实现 |
| C. 模板方法 | 抽象基类固定流程，子类实现钩子 | 复用流程 | 继承耦合强；策略间只有“初始状态”差异，继承过重 |
| D. 表驱动规则 | 用配置表描述状态与条件 | 配置灵活 | 规则表达力弱；复杂条件需自建解释器；调试困难 |

### 2.2 决策

**选择 B：策略模式 + 工厂/注册表。**

理由：

- 各报名方式的差异**仅在“初始状态决策”**，接口可以非常小（`decide(ctx)`），符合接口隔离；
- 公共规则（活动状态、重复报名、权限）留在 `RegistrationService`，避免策略类重复实现；
- `PolicyFactory` 以注册表方式维护 `policyType → policy`，新增方式只需新增类并注册；
- CR-01 的实际验证：新增候补方式只增加 `WaitlistRegistrationPolicy`，`RegistrationService.register()` 主体未改（仅在候补时分配序号）。

### 2.3 后果

- 正面：报名方式可扩展；策略无仓储依赖，单测简单；活动表只存 `policy_type` 字符串。
- 负面：新增一个类与一次注册；需要保证工厂在装配根统一注册。
- 风险控制：`PolicyFactory.create()` 对未知类型抛 `INVALID_POLICY`；测试覆盖三种方式。

## 3. 变化点二：通知渠道

### 3.1 候选方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 服务内直接调用 | `NotificationService` 内依次写消息、发邮件 | 直观 | 新增渠道必须改服务；渠道故障可能影响主流程 |
| B. 观察者模式 | 业务发布领域事件，通知服务订阅 | 业务与通知解耦；可多订阅者；失败隔离 | 事件模型与幂等需要额外设计 |
| C. 装饰器/责任链 | 渠道层层包装 | 组合灵活 | 对“多渠道并行投递”不自然；调试链路长 |
| D. 消息队列 | 外置 MQ 异步消费 | 削峰、可靠 | 课程项目引入运维成本，超出范围 |

### 3.2 决策

**选择 B：观察者（领域事件 + 事件总线），渠道以策略/组合方式注入通知服务。**

理由：

- 报名事务提交后再发事件，天然满足“通知失败不回滚报名”；
- `NotificationService` 依赖渠道列表，新增渠道只改装配根；
- 用 `(event_id, channel)` 唯一约束实现渠道级幂等，重试安全；
- CR-01 的实际验证：新增 `EmailNotificationChannel` 与 `EmailRepository`，业务服务零改动，仅 `app.js` 多注册一个渠道。

### 3.3 后果

- 正面：通知可扩展、失败可留痕、可重放；报名主流程稳定。
- 负面：事件是进程内同步分发，进程崩溃时可能丢失未投递通知（课程规模可接受；生产可换 MQ）。
- 风险控制：订阅者异常被总线捕获并写失败日志；通知日志唯一约束防重复。

## 4. 其他模式决策

| 模式 | 采用 | 备选 | 理由 |
| --- | --- | --- | --- |
| 仓储模式 | 采用 | 服务内直接写 SQL / ActiveRecord | 隔离 SQL，测试可替换；实体保持纯净 |
| 依赖注入 | 采用（装配根 `app.js`） | 模块内单例 | 便于注入临时数据库与固定时钟，测试独立 |
| 工厂 + 注册表 | 采用 | switch 创建 | 新增策略无需修改工厂 switch |
| 软删除 | 采用（CR-01） | 物理删除 / 级联删除 | 保留历史报名与统计，避免破坏引用完整性 |
| 状态枚举 + 实体方法 | 采用 | 散落的字符串判断 | 状态语义集中，视图与规则一致 |

## 5. 设计原则落实

| 原则 | 落实点 |
| --- | --- |
| 单一职责 | Service 编排、Policy 决策、Repository 持久化、View 渲染、Channel 投递 |
| 开闭原则 | 报名方式与通知渠道均以“新增类 + 注册”扩展 |
| 里氏替换 | 所有策略实现同一决策契约；所有渠道实现同一 `send(event)` |
| 接口隔离 | 策略只接收决策所需上下文；渠道只接收事件 |
| 依赖倒置 | 服务依赖仓储与策略抽象；具体实现由装配根注入 |

- 回归用例全部通过，说明变更未破坏既有行为。

## 7. 被否决方案的复盘

1. **if/else**：在只有两种方式时最省事，但 CR-01 会迫使修改核心方法，且分支继续膨胀，故否决。
2. **装饰器做通知**：渠道之间是并列关系而非叠加关系，装饰器会导致调用链不直观，故否决。
3. **外置消息队列**：超出课程项目运维范围，进程内事件总线已满足“解耦 + 失败隔离”，故不采用。
4. **物理删除 + 级联删除报名**：会丢失统计与通知历史，且不可恢复，故改为软删除。
