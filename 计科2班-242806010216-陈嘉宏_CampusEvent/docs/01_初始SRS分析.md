## 1. 文档目的与范围

本文档给出系统**初版**（需求变更 CR-01 之前）的需求规格，作为设计、实现与测试的依据。覆盖校园活动的发布、浏览、报名、审批、取消与通知全流程。

不在范围内：与学校统一身份认证对接、真实短信/邮件网关、在线支付、场地审批、活动签到。

## 2. 项目背景与目标

学校社团与院系每学期组织大量活动，报名依赖微信群接龙或线下表格，存在名额超卖、重复报名、审批无记录、通知遗漏等问题。本系统提供统一入口：

- 学生：浏览活动、按规则报名、查看结果、接收通知；
- 管理员：发布与维护活动、审核报名、查看统计。

目标：用可维护的分层结构与设计模式实现“报名方式可扩展”，为后续需求变更（CR-01）预留演进空间。

## 3. 参与者（Actor）

| 参与者 | 说明 | 主要权限 |
| --- | --- | --- |
| 学生（Student） | 在校学生，使用学号登录 | 浏览/筛选活动、查看详情、报名、取消报名、查看我的报名、查看站内消息 |
| 管理员（Admin） | 活动组织方 | 学生全部权限 + 创建/编辑/删除活动、审批报名、查看统计与待审核列表 |
| 通知渠道（外部系统） | 站内消息；初版仅站内消息 | 接收领域事件并投递通知 |

## 4. 术语

| 术语 | 定义 |
| --- | --- |
| 直接报名（direct） | 名额未满即自动通过，满员即失败 |
| 审核报名（approval） | 提交后为“待审核”，由管理员批准/拒绝，批准时二次校验名额 |
| 有效报名 | 状态为 `pending` / `approved` 的报名记录（v2 增加 `waitlisted`） |
| 名额 | 活动允许的“已通过”人数上限 |
| 领域事件 | 报名状态变化产生的事件，如 submitted / approved / rejected / cancelled |
| 通知留痕 | 每个事件在每个渠道的投递结果记录，用于幂等与排障 |

## 5. 功能需求

| 编号 | 名称 | 描述 | 优先级 |
| --- | --- | --- | --- |
| P2-F01 | 活动浏览与筛选 | 学生查看活动列表，按名称关键字、分类、报名方式筛选 | 高 |
| P2-F02 | 两种报名方式 | 活动创建时选择直接报名或审核报名 | 高 |
| P2-F03 | 名额上限控制 | 直接报名满员失败；审批通过时再次校验，已通过人数不得超过容量 | 高 |
| P2-F04 | 管理员审核 | 管理员查看待审核列表，批准或拒绝，并记录处理结果 | 高 |
| P2-F05 | 重复报名校验 | 同一学生对同一活动最多存在一条有效报名 | 高 |
| P2-F06 | 取消报名 | 学生可取消自己的待审核/已通过报名，释放名额 | 中 |
| P2-F07 | 站内通知 | 报名提交、批准、拒绝、取消后写入站内消息 | 高 |
| P2-F08 | 报名统计 | 管理员查看已通过、待审核、已拒绝、已取消人数与剩余名额 | 中 |
| P2-F09 | 登录与会话 | 学号/管理员账号 + 口令登录，Cookie 会话，角色鉴权 | 高 |
| P2-F10 | 活动管理 | 管理员创建、编辑、删除活动；字段合法性校验 | 高 |

### 5.1 关键功能详细说明

**P2-F02 报名方式**：活动实体持有 `policyType`。报名时由策略对象决定初始状态：直接报名返回 `approved`（名额不足则拒绝），审核报名返回 `pending`。业务规则（活动存在、已开始、重复报名、权限）不随方式变化。

**P2-F03 名额控制**：以“已通过人数”作为占用量。直接报名在决策时判断；审核报名在批准事务内重新统计并校验，避免并发超卖（SQLite 事务串行化）。

**P2-F06 取消**：仅本人可取消；`cancelled` 为终态，允许重新报名。取消后统计立即更新。

**P2-F07 通知**：报名事务提交后发布领域事件，通知服务订阅事件并投递。通知失败只记录失败日志，不回滚报名事务；同一事件同一渠道只投递一次。

## 6. 业务规则

| 编号 | 规则 | 校验位置 |
| --- | --- | --- |
| BR-01 | 活动名称 1—80 字，分类 1—40 字，地点 1—100 字 | ActivityService.validate |
| BR-02 | 容量为 1—5000 的整数 | ActivityService.validate |
| BR-03 | 开始时间必须晚于当前时间 | ActivityService.validate |
| BR-04 | 容量不得小于已通过人数 | ActivityService.update |
| BR-05 | 已有报名记录的活动不得修改报名方式 | ActivityService.update |
| BR-06 | 活动开始后不允许新增报名 | RegistrationService.register |
| BR-07 | 同一活动同一学生只能有一条有效报名 | RegistrationService.register |
| BR-08 | 批准时已通过人数不得达到容量 | RegistrationService.approve |
| BR-09 | 只能取消自己的报名，且状态为 pending/approved | RegistrationService.cancel |
| BR-10 | 学生不能访问管理后台，管理员接口需二次校验角色 | Router 守卫 + Service.assertAdmin |
| BR-11 | 同一事件同一渠道的通知只投递一次 | NotificationService + notification_log 唯一约束 |

## 7. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 可维护性 | 分层清晰；新增报名方式不修改主流程；业务规则集中在 Service |
| 可测试性 | 领域层与 Web 层解耦；测试使用临时 SQLite 与随机端口 |
| 性能 | 单实例 100 并发内，页面响应 < 500 ms；sql.js 内存数据库 + 事务提交落盘 |
| 可靠性 | 报名与名额校验在同一事务；通知失败不影响主流程且可追踪 |
| 安全性 | 口令加盐 SHA-256 存储；HttpOnly Cookie 会话；服务端角色校验；输出 HTML 转义防 XSS |
| 可部署性 | 零第三方运行时依赖；提供 build.sh/run.sh；监听 `0.0.0.0:$PORT` |
| 兼容性 | Node.js 20+，现代浏览器 |

## 8. 约束与假设

- 课程推荐 Python + Flask，但公网托管通道仅支持 Node.js 20 / 静态站点，故采用 Node.js 原生 http + sql.js 实现；分层与设计模式不依赖语言。
- 数据库使用单文件 SQLite（sql.js WASM），无独立数据库服务；单实例部署。
- 通知渠道初版为站内消息；邮件等外部渠道在 CR-01 中扩展。
- 演示数据在数据库为空时自动写入，活动时间相对启动时间生成。

## 9. 验收标准（初版）

1. 演示账号可登录，错误口令被拒绝，未登录访问受保护页面跳转登录页。
2. 管理员可创建两种报名方式的活动；非法字段不写入数据库。
3. 直接报名名额未满自动通过、满员失败；重复报名被拒绝。
4. 审核报名提交为待审核，管理员批准/拒绝后状态正确且产生通知。
5. 批准时名额已满则失败，已通过人数不超过容量。
6. 学生可取消报名，统计同步且可重新报名；活动开始后不能报名。
7. 服务重启后活动、报名、通知数据仍存在。
8. 通知渠道故障不影响报名结果，失败有留痕，重复事件不重复通知。

## 10. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 云平台只允许写临时目录 | 重启后数据丢失 | 演示数据自动重建；文档说明；本地可配置持久目录 |
| sql.js 全量落盘 | 高并发写放大 | 事务合并写；课程规模足够 |
| 需求变更（候补/多渠道） | 主流程被破坏 | 用策略与观察者模式隔离变化点 |
