# 08 变更影响分析（CR-01）

> 对应变更单：`docs/07_变更单CR-01.md`
> 对比基线：`baseline-v1`　目标版本：`change-v2`

## 1. 分析结论摘要

| 结论 | 说明 |
| --- | --- |
| 变化点命中设计预留 | 报名方式与通知渠道分别由策略模式、观察者模式隔离，新增功能以“加类 + 注册”为主 |
| 核心服务改动可控 | `RegistrationService` 增加候补序号与递补逻辑、归档校验；`ActivityService` 的删除改为归档并新增恢复 |
| 数据库为增量迁移 | 002 仅新增列、索引与新表，不删除/重命名既有结构，旧数据可直接升级 |
| 回归风险低 | 初版 19 个用例全部通过，新增 4 个 CR 用例，共 23 个用例 0 失败 |
| 主要风险 | 递补与取消的事务原子性、通知渠道增加后的幂等、归档后的历史数据可见性 |

## 2. 影响范围（按层）

### 2.5 数据层

| 文件 | 变更 |
| --- | --- |
| `db/migrations/002_change_v2.sql` | `activities.status`（默认 active + 检查约束）；`registrations.waitlist_seq`；候补查询索引；`email_outbox` 表（`UNIQUE(event_id, student_id)`） |
| `repository/activityRepository.js` | 学生列表强制 `status='active'`；新增 `setStatus` |
| `repository/registrationRepository.js` | 创建支持 `waitlistSeq`；统计含 waitlisted；新增 `findWaitlistHead`；`listByStudent` 返回候补序号 |
| `repository/notificationLogRepository.js` | 无结构变化，继续按 `(event_id, channel)` 幂等 |

迁移脚本为增量式：

```sql
ALTER TABLE activities ADD COLUMN status TEXT NOT NULL DEFAULT 'active';
ALTER TABLE registrations ADD COLUMN waitlist_seq INTEGER;
CREATE INDEX idx_reg_waitlist ON registrations(activity_id, status, waitlist_seq);
CREATE TABLE email_outbox (... UNIQUE(event_id, student_id));
```

旧库启动时由 `PRAGMA user_version` 从 1 升到 2，已有活动自动获得 `active`。

## 4. 风险分析与应对

| 风险 | 概率 | 影响 | 应对措施 | 结果 |
| --- | --- | --- | --- | --- |
| 取消与递补非原子，导致名额丢失或超发 | 中 | 高 | 取消 + 递补放在同一 `db.transaction`；递补循环以剩余名额为终止条件 | 已实现，v2 用例 2 验证 |
| 递补后候补位次不连续 | 中 | 低 | 位次仅用于展示与排序；递补按 `waitlist_seq` 升序，不要求连续 | 已接受 |
| 双渠道导致重复通知 | 中 | 中 | `notification_log(event_id, channel)` 唯一约束；发件箱 `UNIQUE(event_id, student_id)` | 已实现，幂等用例通过 |
| 归档活动仍可被报名/审批 | 中 | 高 | 服务层统一校验 `isArchived()`；学生列表 SQL 过滤 | 已实现，v2 用例 4 验证 |
| 迁移破坏旧数据 | 低 | 高 | 增量 DDL + 默认值；启动自动迁移；测试临时库从 0 建库 | 通过 |
| 既有测试语义冲突（物理删除→归档） | 高 | 中 | 明确更新该用例并在回归表标注“语义变更” | 已更新，通过 |

## 5. 实施步骤（实际执行顺序）

1. 更新枚举与实体，定义候补状态与归档状态；
2. 新增迁移 `002_change_v2.sql`，调整仓储；
3. 新增候补策略并注册到工厂；
4. 改造 `RegistrationService`（归档校验、候补序号、递补、事件）；
5. 改造 `ActivityService`（归档/恢复、统计、编辑限制）；
6. 新增邮件渠道与发件箱仓储，通知服务支持多渠道；
7. 装配根接入新依赖，Web 路由与视图增加入口；
8. 更新初版测试语义，新增 4 个 CR 用例；
9. 全量执行 `node --test`，修复回归；
10. 更新 README、AI_DEV_LOG 与文档，提交并打标签；
11. 公网部署并验证。

## 6. 验证结果

- 自动化测试：`node --test` → **23 通过 / 0 失败**，耗时约 0.7 s；
- 手工验证（公网）：登录页可访问，演示账号 `s1001` 登录成功并加载 4 个活动；候补/递补、归档/恢复、邮件记录由本地 23 个用例覆盖（公网实例与本地使用同一构建产物）。
- 数据迁移：旧库（v1）启动后自动升级，既有活动状态为 active；
- 部署：FunctionWeb（Node.js 20）构建成功，公网地址见 README。

## 7. 回滚方案

| 场景 | 回滚方式 |
| --- | --- |
| 代码回归 | 切换到 `baseline-v1` 标签重新部署 |
| 数据迁移 | 002 只做增量；如需回退，可删除新增列/表后把 `PRAGMA user_version` 置回 1（会丢失候补与邮件数据） |
| 单个活动误归档 | 管理员点击“恢复”，无需回滚代码 |
| 通知渠道异常 | 在装配根移除邮件渠道即可降级为单渠道，业务不受影响 |
